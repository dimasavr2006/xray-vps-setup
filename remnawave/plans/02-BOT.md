# План 02 — адаптация Telegram-бота к Remnawave

Статус: **не реализован**. Решения зафиксированы 07.10.2026.
Связанные документы: [общий проект](../README.md), [установщик](01-INSTALLER.md),
[миграция](03-MIGRATION.md).

## 1. Цель и исходная архитектура

Сохранить пользовательские функции PDM VPN при замене API панели.
Не заменять существующий бот сторонним: он уже содержит семейные группы,
права главы, индивидуальные квоты, устойчивые операции и уведомления.

В `../../telegram_bot/src/vpn_bot/panel.py` есть `PanelGateway`, реализация
Marzneshin и тестовый FakePanelGateway. Runtime сейчас создаёт MarzneshinGateway
напрямую. Domain-модели используют числовые ID; NodeCode ограничен LT/FI/SE.
Основная SQLite на зафиксированном рабочем выпуске имеет schema 23.

Сначала сохранить весь действующий путь Marzneshin и добавить второй адаптер.
Работать поверх текущих файлов, включая незакоммиченные изменения; не подменять
их старой версией из Git. Резервные копии состояния не открывать через код,
который автоматически применяет миграции к оригиналу.

## 2. Интерфейсы и соответствия

Добавить фабрику панели и настройки:

| Настройка | Назначение |
| --- | --- |
| `VPN_BOT_PANEL_PROVIDER` | `marzneshin` или `remnawave`; прежний вариант — default |
| `VPN_BOT_PANEL_API_TOKEN_FILE` | Файл токена Remnawave вместо логина/пароля Marzneshin |
| `VPN_BOT_PANEL_IDENTITY` | Существующая обязательная изоляция окружений |
| `VPN_BOT_STATS_BASE_URL` | Внутренний API точной по интервалам статистики |
| `VPN_BOT_STATS_TOKEN_FILE` | Авторизация к статистике |

`RemnawaveGateway` реализует операции существующего PanelGateway:
каталог, создание/поиск пользователя, срок, заметка, состояние, подписка,
назначения доступа, ноды и история трафика. Ограничить параллелизм и таймауты;
разделить ошибку авторизации, недоступность и несовместимый ответ API.

Для Remnawave 3.4.5 пользователь имеет числовой ID; ноды, профили и squads
используют UUID. Сохранить локальные числовые идентификаторы предметных
моделей через постоянную таблицу внешних соответствий в SQLite. Записи
изолируются по `panel_identity` и типу сущности; нельзя усекать UUID, хешировать
его в int или сопоставлять объекты по порядку получения.

Семантика доступа: `PanelService` соответствует проверенному набору inbounds
в internal squad. Клиентская группа принадлежит одной логической ноде и
одному транспорту. Технические группы никогда не предлагаются обычному
пользователю. Состав семейной подписки бота не является internal squad Remnawave.

Реестр нод заменить на расширяемый стабильный код, имя, страну и внешнее
соответствие. LT/FI/SE сохранить без изменений кодов. Новая нода появляется
в управлении после явной регистрации; её добавление не раздаёт доступ всем.
Существующие специфичные правила SE остаются привязаны к SE.

## 3. Поведение пользователя и администратора

Сохранить профиль, ссылки, инструкции приложений, трафик, покупку/продление
через контакт, личные привязки, приглашения и явные семейные группы.
Глава получает только ссылки текущих участников своей группы; проверять
полномочия повторно после обращения к панели, как в текущей реализации.

Сохранить административное создание, продление, дату, отключение, заметку,
доступ к странам/протоколам, управление нодами, квотами и уведомлениями.
Модификации сохраняют фиксированную цель до API-запроса и сверяются после
таймаута. Групповой срок восстанавливается после частичного выполнения.

Бессрочный доступ хранить отдельным признаком в состоянии бота. На границе
Remnawave использовать документированный для проекта sentinel
`2099-12-31T15:13:22.214Z`, совпадающий с официальным переносчиком. Только
аккаунты с явным признаком показывать как бессрочные; саму далёкую дату
не считать доказательством бессрочности.

Установить capability-флаги адаптера: режим START_ON_FIRST_USE не объявлять
поддержанным без отдельной реализации. При его наличии в свежем источнике
предварительная проверка миграции требует решения, а не преобразует его
в фиксированный срок. В исследованном снимке неудалённые аккаунты имеют
FIXED_DATE или NEVER.

Не включать HWID-ограничения при переходе: такого изменения пользователь
не запрашивал. Ссылки новых подписок получать у Remnawave; старые ссылки
можно распознавать по миграционной таблице только для проверки уже
существующей привязки, без публичного раскрытия секретов.

## 4. Трафик и квоты

### Источник интервальной статистики

Штатная пользовательская история Remnawave 3.4.5 агрегирована по дням UTC
и имеет ограниченную ретенцию. Нельзя выдать сумму суток UTC за московский
месяц или обещать восстановить отсутствующие почасовые данные задним числом.

Реализовать дополнение `stats/` на стороне новой панели:

1. Версионированная собственная схема PostgreSQL `pdm_stats`.
2. Транзакционный AFTER-триггер на штатной пользовательской истории сохраняет
   положительное приращение total_bytes с временем наблюдения и ID ноды/пользователя.
   Для UPSERT учитывать INSERT/UPDATE-семантику, исключающую двойной учёт.
3. Очистка старых строк панели не удаляет собственную историю. Понижение
   счётчика/пересоздание ряда не превращается в отрицательный пользовательский
   расход: фиксируется новая эпоха и состояние неполноты для спорного интервала.
4. Данные уплотняются в часовые корзины UTC после закрытия интервала; перенос
   исходных данных сохраняет собственную provenance и точку отсечения.
5. Внутренний HTTP API выдаёт пользователя, интервал `[start,end)`, суммы по
   нодам, coverage, unknown_bytes, время наблюдения и состояние полноты.
6. Read-only учётная запись stats API имеет доступ только к необходимым данным;
   служба не доступна из Интернета. Бот не получает доступ к основной БД панели.

Часовые корзины позволяют выделить 21:00 UTC — начало московских суток.
Точность остаётся точностью момента поступления выборки, а не времени каждого
пакета. Для произвольной границы миграции сохранять отдельный checkpoint,
не округляя его до часа. Пропущенное измерение не считать подтверждённым нулём.

Это **проектируемое дополнение**, ещё не испытанное на Remnawave. До включения
личных автоограничений обязательны тесты транзакций, рестартов, сбросов,
задержек и смены суток. Сигнатура схемы проверяется перед upgrade; при
несовместимости обновление останавливается до адаптации дополнения.
Не запускать параллельный poller Xray, который сбрасывает счётчики панели.

### Сохранение бизнес-правил

- Месяц личных лимитов: 1-е число, 00:00 Europe/Moscow.
- Существующие доли SE текущего месяца и исключения переносятся без пересчёта.
- Расход = историческая часть до перехода + новая часть после checkpoint,
  с раздельными источниками и без повторного сложения baseline.
- Размер лимита, использованный объём и остаток — разные величины. Сохранять
  все три; штатный импорт только размера лимита не завершает перенос.
- Для персональных правил бота он остаётся владельцем enforcement. Нативный
  MONTH панели не использовать как замену московскому периоду.
- Панельные лимиты источника требуют явного преобразования остатка и стратегии:
  не применять одновременно два несогласованных механизма сброса.
- USER_NODE снимает только нужные группы доступа. USER_TOTAL сохраняет
  корректное полное отключение; ручные запреты и активные holds не теряются.

### Общая квота сервера

Переиспользовать имеющийся quota-agent и протокол ограниченного SSH. Один
агент на хост считает RX+TX всего интерфейса, в том числе транзит и соседние
службы. Накопление, период и исходная точка не меняются от смены панели.
Тестовый бот читает рабочие агенты, но не управляет их защитой.

## 5. SQLite, тестовый режим и переключение

Добавить явную версию миграции SQLite, внешние соответствия, metadata
бессрочности и источников исторического расхода. Прогнать миграции на копии
schema 23 с integrity_check и foreign_key_check; обеспечить совместимый
Marzneshin-путь. Перед откатом на более старый код использовать совместимую
БД, а не предполагать автоматическую обратную совместимость новой схемы.

Тестовый контур: отдельные token, SQLite, panel_identity, поколение callback,
Telegram offset и allowlist администратора. Получателей рабочих уведомлений
не активировать. Для другого токена нужен отдельно загруженный тестовый APK:
производственный file_id не является переносимым между ботами.

При рабочем переходе токен основного бота сохраняется. Импорт SQLite и
переключение выполняет план 03 при остановленном основном poller. Одновременно
работает только один poller этого токена; аренда одной SQLite не защищает от
случайного запуска второго poller с другой базой.

## 6. Проверки и критерии завершения

- [ ] Старые тесты Marzneshin проходят; новый адаптер имеет контрактные тесты под закреплённую версию.
- [ ] Создание, продление и группа восстанавливаются после потерянных ответов без повторного изменения.
- [ ] UUID/ID не смешиваются между панелями; смена порядка каталога не меняет соответствия.
- [ ] Права главы и личные ссылки выдерживают смену состава группы во время запроса.
- [ ] Добавление новой ноды не требует изменения enum и не меняет права старых пользователей.
- [ ] Московская граница месяца и поздние выборки проверены, неизвестная история не становится нулём.
- [ ] INSERT/UPSERT/rollback транзакции, рестарт, сброс счётчика и очистка панели не удваивают расход.
- [ ] Суммы собственного учёта сверены с панелью за полностью покрытый общий интервал.
- [ ] Переносимые доли SE, остатки и holds сохраняются после перезапуска.
- [ ] Новое уведомление не повторяет уже доставленное; тестовый бот не пишет пользователям.
- [ ] Пройдены Ruff, mypy, существующий набор тестов и новые регрессии; выполнена приёмка интерфейса.

Передача миграции: проверенный образ бота, версия SQLite, спецификация mapping,
средство импорта/сверки состояния и документация ограничения статистики.
