# План 03 — перенос Marzneshin, Telegram-бота и всей обвязки

Статус: **не реализован; рабочий перенос не запускался**.
Решения зафиксированы 07.10.2026.
Зависимости: [установщик](01-INSTALLER.md), [бот](02-BOT.md).

## 1. Цель и состав переноса

Перейти на Remnawave с сохранением аккаунтов, Telegram-привязок, сроков,
доступа, семейных групп, расхода, остатка квот и поведения маршрутизации.
Новые ссылки подписок разрешены; совместимость полного старого URL не является
критерием приёмки. Существующие VLESS UUID и совместимые параметры нод сохранять.

Перенос разделён на три исполняемых шага под одной командой управления:
официальный переносчик аккаунтов с доработками; настройки инфраструктуры;
состояние бота и учёт. Его результаты сверяются независимо от exit code.

## 2. Использование официального remnawave-migrate

Основа — опубликованный v2.1.0 проекта `remnawave/migrate`, режим
`--panel-type=marzneshin`. Он переносит аккаунты, UUID из подписок, сроки,
даты создания, заметки, размеры лимитов; сохранение статуса включается явно.
Существующие пользователи штатно пропускаются, использованный трафик не
переносится, короткие имена дополняются подчёркиваниями.

Создать минимальную сопровождаемую доработку в `migration/`, с указанием
upstream tag/commit, лицензии и списка патчей. Не называть изменённую сборку
неизменённым официальным бинарником. Проверить её с API выбранной панели.

Обязательные дополнения:

- `preview`, явный список ID аккаунтов, журнал операций и JSON-отчёт без секретов.
- Сохранение имён, допустимых в целевой панели; предварительная проверка
  коллизий. Не дополнять имена до шести символов. По снимку есть шесть
  неудалённых аккаунтов с именами длиной четыре/пять символов.
- Корректная пагинация и выборка указанных аккаунтов. Штатный `--last-users`
  не считать точным способом выбрать тестовую группу без проверки.
- Исключение удалённых записей; отдельный список технических пользователей.
- Получение и сверка VLESS UUID до записи. Если подписка недоступна или пуста,
  взять ключ из авторизованного экспорта конфигурации/согласованной копии БД;
  при отсутствии проверенного значения остановиться, не генерировать новый молча.
- Сохранение FIXED_DATE и NEVER; отдельная metadata бессрочности по плану 02.
  Режим первого использования не конвертировать без реализованной поддержки.
- Точное преобразование ручного отключения, истечения и исчерпанного лимита
  в допустимые состояния выбранного API. Не включать всех по default ACTIVE.
- HTTP-таймауты, сверка после потери ответа, bounded retry, ошибка процесса
  при незавершённых аккаунтах и возможность безопасно продолжить.
- Повторный запуск сверяет поля и применяет разрешённую дельту к объектам,
  принадлежащим данной миграции; чужое совпадающее имя — конфликт.

Первый импорт — без internal squads: он не предоставляет VPN-доступ.
Отдельный шаг назначает каждому исходный набор разрешённых клиентских входов.
Не использовать один общий `--internal-squad` для выдачи всех стран всем.
`--preserve-subhash` по умолчанию выключен: новые ссылки допустимы.

## 3. Предварительная инвентаризация и артефакты

Получить свежие согласованные backup панели, бота, конфигов нод и агентов.
Исторические файлы 7 октября использовать как ориентир; перед применением
сверить активные значения и отказываться перезаписывать неожиданное состояние.

Зафиксировать пользователей, transport UUID, сроки, состояния, Services и
фактические inbounds, ссылки, историю/счётчики, группы, holds, распределения,
незавершённые операции, статусы нод, образы, порты, сертификаты и маршруты.
Секретный экспорт хранить отдельно; публичный отчёт содержит количества,
контрольные суммы и результаты сравнений.

Планируемые команды: `migration preview`, `migration apply`,
`migration verify`, `migration rollback`. Выбор окружения и идентификатор
миграции обязательны. Режим preview использует только чтение источника.

Постоянные артефакты:

| Файл | Содержание |
| --- | --- |
| `migration-map.json` | source/target identity; old user ID → target ID; соответствия нод, Services, inbounds и squads |
| `migration-state.json` | Шаги, фиксированные цели, контрольные суммы и результаты повторов |
| `verification.json` | Успех/ошибка по проверкам, отсутствующие и несовпадающие объекты |
| `traffic-checkpoints.json` | Границы перехода каждой ноды, baseline и полнота источников |

Имена и ID также являются частными данными; артефакты реальной миграции
не публикуются. UUID доступа, токены и URL подписок в отчёт не включаются.

## 4. Конфиги, доступ и серверная обвязка

Преобразовывать Services по набору inbounds, а не по имени. Каждой стране
и транспорту соответствует отдельная клиентская группа. Смешанные старые
Services разворачиваются в точный набор этих групп. Неподдерживаемый вход
показывается как несовпадение; его нельзя потерять незаметно.

Технические пользователи и CHAIN-inbounds переносятся отдельно и не появляются
в обычных подписках. Сохранить текущие работающие Reality-ключи, SNI, short ID,
XHTTP-пути и клиентские UUID; сгенерированные тестовые параметры не подменяют
производственные при окончательном переключении.

| Компонент | Сохраняемое поведение |
| --- | --- |
| LT, обычный трафик | Текущий выход IPv4 |
| Twitch с LT | FI с резервом LT; MSS 1200 на соответствующих выходах |
| Telegram с LT | SE с резервом LT; отдельные правила доменов и IP |
| Gemini | Имеющиеся выходы через IPv6 |
| Приватная сеть 10.66.66.0/24 | FI/SE → LT через технические подключения |
| Серверная квота | Тот же внешний интерфейс, накопление, reset и защита |

Проверять реальные конфиги и доступность, а не только наличие правил.
Observatory проверяет транспортную доступность, не гарантирует доступность
конкретного приложения; тестировать Telegram/Twitch отдельно.

Агенты квот не переустанавливать поверх состояния. SE сохраняет 2 TB RX+TX,
100 GB резерва, порог 1,9 TB и сброс 7-го в 00:00 Europe/Stockholm.
Проверить FI/LT по свежему inventory. На переходе защита охватывает старые и
новые VPN-порты, оставляя доступ к управлению и панели 9443.

## 5. Состояние Telegram-бота и трафик

Импортировать SQLite в отдельное окружение с явным mapping всех панельных
ссылок, включая ID внутри сохранённых JSON операций. Простой SQL replace ID
недостаточен. Сохранить контакты, подтверждённые связи, группы/глав, сроки,
политики, access intent, holds, доли и пулы SE, исключения, настройки контента,
историю уведомлений и журнал. Старые черновики подтверждений инвалидировать
новым поколением интерфейса; незавершённые операции разрешить до финального
переключения либо явно отметить как требующие разбора, не проигрывать вслепую.

Старые приглашения сохранять только с корректно преобразованной целью;
нельзя позволить приглашению привязать аккаунт другой панели. Недоставленные
уведомления пересчитывать по актуальному состоянию, сохраняя дедупликацию
доставленных. Runtime lease и pending Telegram updates не копировать в
активный тестовый процесс; рабочий offset переносить при остановленном poller.

Использовать полноценный импорт, а не существующий `vpn-state-migrate`,
который специально исключает связи, политики, holds и историю.

Историю старой панели хранить отдельным источником, а не подделывать её
записью в штатные таблицы Remnawave. Исходный lifetime расход и месячные суммы
сочетаются с новой статистикой по checkpoint каждой ноды. Не считать
одновременно один и тот же интервал как старый и новый.

Сохранять величину исходного лимита и уже использованную часть. Нативный
импорт полного лимита не должен выдать его повторно. Для источниковых
панельных лимитов заранее вычислять остаток; исчерпанный остаток означает
ограничение, а не `0 = unlimited`. Проверять reset-стратегию отдельно от
личных политик бота и не сдвигать московский месяц на UTC.

Группы и доли текущего месяца не пересоздавать по сегодняшнему количеству
аккаунтов. Уведомления основным пользователям во время репетиции запрещены
техническим режимом allowlist/sink, а не только договорённостью оператора.

## 6. Репетиция и рабочее переключение

### Репетиция

1. Проверить fixture-набор переносчика и восстановление после ошибок.
2. Поднять чистую целевую панель по плану 01, включить stats до тестового трафика.
3. Импортировать копию каталога и SQLite; проверить каждый mapping и доступ.
4. Использовать отдельные тестовые аккаунты для живого VPN и тестового бота.
5. Сверить полный отчёт, проверить восстановление и провести минимум 48 часов
   наблюдения нагрузки и стабильности FI. Тестовый расход отделён от рабочего.

### Условия начала рабочего окна

Установщик, адаптер и переносчик прошли приёмку; ресурсная проверка разрешает
рабочее размещение; известны домены; backup проверен вне VPS; нет неразрешённых
операций/коллизий и пропущенных аккаунтов. Согласовано рабочее окно переключения.

### Последовательность

1. Остановить основной Telegram poller и запретить административные изменения.
   Пользовательский VPN продолжает работать до замены соответствующей ноды.
2. Сделать окончательную согласованную копию, сверить изменения с репетицией,
   применить дельту аккаунтов/доступа и импорт состояния.
3. Переключать ноды FI → SE → LT. Перед остановкой старой ноды получить
   последнюю подтверждённую статистику; зафиксировать границу и полноту.
   Запустить Remnawave на 443/8443 и проверить оба транспорта и зависимые маршруты.
4. Сохранённые параметры позволяют старым клиентским профилям продолжить работу
   там, где совместимость подтверждена тестом. Гарантировать это до испытаний нельзя.
5. Финализировать историю, остатки, holds и контрольные суммы SQLite.
6. Запустить один основной бот с прежним токеном и новым provider/identity.
   Проверить offset/lease, семейные группы и отсутствие повторных уведомлений.
7. Новые ссылки выдаются обычными кнопками бота. Массовая рассылка не является
   частью автоматического переключения и не запускается без отдельной задачи.
8. Старые контейнеры оставить остановленными и восстановимыми; не удалять
   их автоматически после успешного healthcheck.

## 7. Откат

До изменения рабочих нод откат удаляет только принадлежащие стенду результаты
или восстанавливает его backup; источник продолжает быть авторитетным.

Во время окна до запуска основного бота вернуть прежние ноды и конфиги,
сохранив уже измеренный новый трафик в журнале перехода.

После начала работы Remnawave сначала остановить записи, перенести обратно
новые аккаунты, продления, состояния, назначения и прирост расхода по mapping,
сверить результат; только затем переключать ноды и основной бот.
Восстановление старой базы поверх новых событий запрещено: оно теряет данные.
Автоматический откат допускается только для проверяемых преобразований;
необратимое или нераспознанное изменение останавливает откат с отчётом.

## 8. Проверки и критерии завершения

- [ ] Все неудалённые клиентские и нужные технические аккаунты учтены; пропуски отсутствуют.
- [ ] Имена/UUID, точные сроки, признаки бессрочности и ручные запреты сохранены.
- [ ] Недоступная подписка и отсутствие ключа не создают новый UUID автоматически.
- [ ] У каждого аккаунта совпадает фактический разрешённый набор входов.
- [ ] Повторный импорт, обрыв HTTP и конфликт существующего имени обработаны безопасно.
- [ ] Отчёт обнаруживает частичную ошибку даже при успешном завершении upstream CLI.
- [ ] Связи Telegram, группы, права главы, доли, расход и holds совпадают с источником.
- [ ] Проверены UTC/Москва/Стокгольм, переход суток и отсутствие двойного baseline.
- [ ] Реальные LT/FI/SE TCP/XHTTP, приложение подписки и все маршруты прошли проверки.
- [ ] Серверная блокировка сохраняет доступ к управлению и не имеет транзитного обхода квоты.
- [ ] Основной poller один, повторных уведомлений нет, SQLite integrity/FK корректны.
- [ ] Пройдены восстановление из backup и репетиция отката с новым продлением/расходом.
- [ ] Итоговые отчёты, версии, checkpoint и инструкции отката сохранены вне мигрируемого VPS.
