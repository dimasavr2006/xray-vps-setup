# План 01 — установщик Remnawave и отдельных нод

Статус на **09.10.2026: параллельная установка на FI Debian 13 с одним доменом
и текущими 2 GiB RAM выполнена; TCP/XHTTP и HTTPS проверены**.
Три роли, SSH-подключение отдельной ноды, firewall IPv4/IPv6 и обслуживание
прошли на чистом Debian 13 WSL с собственным Docker. FI ACME staging перевыпущен.
Чистый провайдерский VPS и 48 часов наблюдения остаются открытыми.
Решения зафиксированы 07.10.2026.
Связанные документы: [общий проект](../README.md), [бот](02-BOT.md),
[миграция](03-MIGRATION.md).

## 1. Цель и границы

Получить повторяемую установку по одной точке входа, аналогичную по удобству
существующему `xray-vps-setup`: пользователь задаёт домены и параметры,
скрипт создаёт конфиги и запускает проверенный комплект компонентов.

Обязательны независимые сценарии панели и ноды, автоматические сертификаты,
защита сервера, подключение ноды, резервное копирование и обновление.
Этот установщик не переносит пользовательскую базу и не переключает основной бот:
это отдельный план миграции.

Актуальная реализация после уточнения владельца: Bash для подготовки хоста
и Docker Compose; jq для структурированных JSON и curl для API. Python на VPS
не используется. Не формировать JSON
подстановкой произвольных строк через `sed`/`envsubst`.

Уточнение владельца 08.10.2026: **только Linux**, без поддержки Windows/macOS.
Точка входа — самодостаточный Bash-файл, запускаемый как
`bash <(wget -qO- RAW_URL/rw-setup.sh)`; удаление — таким же образом через
`uninstall.sh`. Читаемые Bash-функции, jq-схема и шаблоны объединяются при сборке;
наличие клонированного репозитория на сервере не требуется.

## 2. Пользовательские команды

Планируемая точка входа — `rw-setup.sh`; дальнейшее обслуживание — `rwctl`.

| Команда | Результат |
| --- | --- |
| `rw-setup.sh` | Интерактивный выбор режима и параметров |
| `rw-setup.sh --role panel --config FILE` | Панель без VPN-ноды |
| `rw-setup.sh --role node --config FILE` | Отдельная нода, готовая к подключению |
| `rw-setup.sh --role panel-node --config FILE` | Панель и нода с согласованными портами |
| `rwctl plan / apply` | Просмотр и применение изменений конфигурации |
| `rwctl node attach --ssh HOST --config FILE` | Регистрация ноды и доставка параметров по SSH |
| `rwctl doctor` | Отчёт состояния без изменения сервера |
| `rwctl backup / restore / upgrade` | Управляемое обслуживание |
| `uninstall.sh [--output DIRECTORY] [--dry-run] [--purge]` | Удаление только выбранного окружения, с явной опцией удаления данных |

Все команды записи поддерживают проверку предварительных условий. Повторный
запуск продолжает прерванную операцию либо сообщает конфликт, не меняя ключи.
Удаление и очистка чужих Docker-ресурсов не входят в установку.
Удаление не сбрасывает общий firewall и не удаляет Docker Engine/образы,
чужие службы или неуправляемые файлы. Владение проверяется по manifest и
Compose labels до изменений и повторно после подтверждения.

## 3. Генерируемая система

**Панель:** Remnawave, PostgreSQL, Valkey, Caddy Auth, subscription-page,
healthchecks, ротация журналов, конфигурация backup и manifest установки.
Собственные имена Compose-проектов, сетей и томов исключают совпадения с
`caddy`, `marznode` и другими существующими контейнерами.

**Нода:** официальный Remnawave Node, Caddy с маскировочным сайтом,
VLESS TCP Reality и XHTTP; управление только с адреса панели. Нода не
включает PostgreSQL, панель или Telegram-бота.

**Разделение ответственности:** серверный профиль Xray хранится в панели.
Установщик создаёт/обновляет его через API; не поддерживает конкурирующий
локальный конфиг, который перетирает изменения Remnawave.

Создавать ключи Reality, short ID, XHTTP-путь и системные секреты один раз.
При миграции принимать существующие проверенные параметры из закрытого
пакета; при новой установке генерировать новые.

Первого администратора создавать до публикации панели. Служебные API-токены
выпускать через административный API с минимально нужными правами, хранить
отдельно от manifest, учитывать срок действия и ротацию. Подключение ноды
получает настоящий `SECRET_KEY` штатным API панели; не придумывать собственный
несовместимый протокол авторизации. Полный токен панели на ноду не копировать.

## 4. Режимы сети и HTTPS

| Установка | HTTPS панели | VPN TCP / XHTTP | Управление нодой |
| --- | --- | --- | --- |
| Чистый сервер, только панель | 443 | Нет | Нет |
| Чистый сервер, только нода | Нет | 443 / 8443 | 2222, только от панели |
| Панель и нода на одном IP | 9443 | 443 / 8443 | 2222, локально |
| Параллельный тест на FI | 9443 | 24443 / 28443 | 2222, локально |

Для ноды Caddy обслуживает Reality target на loopback-порту 14123.
Внешний API ноды нельзя путать с клиентским VLESS-портом. Перед применением
проверять все порты и привязки IPv4/IPv6; при конфликте прекращать установку,
а не молча выбирать другой порт. Порты доступны как явные параметры config.

На FI прежняя система сохраняет 80, 443, 8443, 37241, 4123 и 53042.
Новый Caddy использует собственное хранилище сертификатов. Для HTTP-01
существующий Caddy передаёт только `/.well-known/acme-challenge/*` новых
доменов в HTTP-listener нового Caddy на `127.0.0.1:18080`.
Остальные новые HTTP-запросы получают перенаправление на соответствующий
HTTPS URL; прежние домены не изменяются. TLS-ALPN challenge для этого
параллельного режима отключён, поскольку внешний 443 принадлежит Xray.

Правки существующего Caddy: резервная копия, проверка полного конфига,
graceful reload и проверка старого сайта. Повторная установка не добавляет
дублирующий маршрут. Данные сертификатов сохраняются при пересоздании контейнера.

Панель и subscription-page размещаются в корне отдельных сайтов. Уточнение
владельца 09.10.2026: для FI оставить один `fl.wf.md`, панель на 9443, подписки
на 9444, ноду на 24443/28443. Увеличение памяти не требуется для текущего теста:
`compact-test` ограничивает новый стек 1152 MiB и сохраняет 128 MiB запаса.
Для общего домена HTTP-01 добавляется внутрь прежнего HTTP site с сохранением
исходного redirect; повторный блок того же host не создаётся.
Административный домен защищён Caddy Auth с MFA. Публичная страница подписки
не требует административного входа; к API панели обращается служебно.
Владелец самостоятельно завершает привязку аутентификатора при первом входе.
Проверить cookies, redirect URL, CORS и ссылки клиента при HTTPS-порте 9443.

## 5. Безопасность и сохранность хоста

- Перед изменениями: ОС, архитектура, DNS A/AAAA, время, ресурсы, занятые порты,
  существующие Docker/SSH/firewall, работоспособность действующих сервисов.
- Поддерживаемая первая ОС: Debian 13, используемая на FI. Поддержку Ubuntu
  объявлять только после отдельного прогона установки на выбранной версии.
- SSH-ключ и отдельный администратор; существующий вход отключать только после
  проверки нового подключения и корректности `sshd -t`.
- Firewall разрешает заданные публичные порты, ограничивает управление по
  источнику; учитывать обход UFW опубликованными Docker-портами и IPv6.
- PostgreSQL, Valkey, метрики и внутренний stats API не публикуются в Интернет.
- Секретные файлы с минимальными правами; redact журналов; запрет shell tracing
  для операций с секретами. Инвентарь содержит ссылки на secret-файлы, не их содержимое.
- Контейнерам назначать только необходимые права. NET_ADMIN нужен агенту
  защиты квоты, а не панели или Telegram-боту.
- Изменения BBR, SSH, firewall и прочей настройки хоста выводить отдельными
  пунктами предварительного плана; не выполнять безусловный full-upgrade/reboot.

## 6. Подключение новой ноды

1. `node` подготавливает хост и записывает manifest состояния, не требует установки панели.
2. Команда `node attach` на стороне управления проверяет SSH host key и manifest ноды.
3. Создаёт профиль, запись ноды, выбранные inbounds и Hosts через API Remnawave.
4. Доставляет секрет управления по SSH и запускает ноду. Для несетевого обмена
   поддержать защищённый файл параметров с ограниченным временем хранения.
5. Проверяет здоровье, оба транспорта и реальные параметры подписки.
6. Регистрирует ноду и группы доступа в inventory. Выдача доступа существующим
   пользователям выполняется явно, не автоматически всем аккаунтам.

Повторное подключение сверяет уже записанные идентификаторы. Одноимённый
чужой объект считается конфликтом, а не основанием перезаписать его.

## 7. Обслуживание и ресурсы

`backup` включает согласованный dump PostgreSQL, состояния Caddy Auth/MFA и
сертификатов, конфиги, manifest и версии. Для установки с ботом общий процесс
миграции добавляет SQLite и состояние quota-agent. Архив проверяется и хранится
вне мигрируемого хоста. Пароли и архивы не попадают в Git.

`upgrade`: проверка совместимости панели/ноды/статистики, backup, применение
закреплённой версии, healthchecks. При миграции БД откат включает совместимое
восстановление данных; одного возврата старого образа может быть недостаточно.

FI используется только как малый стенд с ротацией логов и ограничениями
ресурсов новых контейнеров. Перед запуском рассчитывать требуемое место для
образов, данных и восстановления. Нехватку ресурсов показывать как причину
остановки, не очищая чужие образы/архивы. Логи, БД и резервные копии не должны
доводить хост до заполнения диска.
